# Green Efficiency Analysis

## Measurement Methodology
All benchmark experiments were conducted within the same isolated Linux environment to maintain consistency across runs. Each C program was compiled using strict flags (gcc -Wall -Werror -Wextra -pedantic -std=gnu89 -Wno-long-long) without compiler optimization flags so that the raw instruction overhead of each implementation could be observed directly. Execution time was measured using the standard C library clock() function from <time.h>, capturing processor ticks at defined phase boundaries and dividing the elapsed ticks by CLOCKS_PER_SEC to obtain values in seconds. To account for runtime variance caused by operating system scheduling, both the baseline loop and the algorithm comparison programs were executed three consecutive times. In the multi-phase instrumentation experiment, four contiguous timestamps (t0 through t3) were recorded immediately before and after build_dataset(), process_dataset(), and reduce_checksum() so that total elapsed time equaled the exact sum of the sub-phases without overlapping overhead.

## Relation Between Runtime and Energy Consumption
Although software benchmarks do not measure physical electrical draw in watts directly, CPU execution time serves as a practical proxy for energy consumption. A processor executing instructions remains in an active power state rather than entering low-power idle states. In our comparison experiment, the naive algorithm kept the CPU actively computing for time: seconds per run compared to time: seconds for the single-pass version. When deployed at scale across thousands of servers or millions of client devices, an O(N^2) implementation multiplies active processor cycles by a factor of 25866.24, directly increasing electricity usage, heat dissipation, and carbon emissions.

## Limitations of the Experiment
Several technical limitations affect these measurements. First, clock() measures processor time allocated to the process rather than actual hardware watt-hours, ignoring thermal throttling, CPU frequency scaling, and memory subsystem power draw. Second, for very fast operations such as the single-pass algorithm (time: seconds) and the instrumentation sub-phases (0.000293 to 0.000136 seconds), the duration approaches the resolution limit of clock(), introducing quantization noise. Finally, running in a shared containerized environment introduces background context-switching jitter that slightly shifts timings between runs.

## Practical Engineering Takeaway
Sustainable software engineering begins with algorithmic discipline and empirical measurement. Before attempting micro-optimizations, developers should instrument code phases to locate actual bottlenecks, as demonstrated in the instrumentation lab where arithmetic-heavy loops dominated runtime.
